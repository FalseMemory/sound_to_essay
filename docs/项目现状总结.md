## 二、已实现的功能（按阶段）

### 阶段 A — 桌面资料安全 ✅
- **先登记后转写**：录音落盘 → 登记记忆与音频资产 → 再转写。转写失败也不丢录音，可重新转写。
- **原始转写永不可删**；编辑只产生新版本，历史可回溯、可恢复（切指针，不复制）。
- **软删除**：记忆移入回收站后可恢复；章节软删保留关联。
- **完整备份与恢复**：`.svbak` 整库快照 + 全部音频；恢复前自动留存"后悔药"副本。

### 阶段 B — 导入与交换协议 ✅
- **音频导入**：`.mp3/.m4a/.mp4/.wav/.ogg/.flac/.webm/...` 共 30 种扩展名（前端选择器、Rust 准入、Python 识别**三处一致**）。
- **素材包协议 v1**（`.svpack`）：`recordId` 跨设备不变，内容改动只递增 `revision`。
- **导入语义四条**：不存在→追加；revision 相同→跳过；**包内 revision 更大→更新**；冲突→保留双方（标题加「冲突副本」）。
- **章节与草稿**：多版本草稿、来源记忆可追溯、章节来源清单支持 AI 生成。
- 内容寻址去重（SHA-256）、模糊事件时间独立保存、不传播删除。

### 阶段 C — 手机记录端 ✅（含真机验收）
- 独立入口 `mobile.html`，与桌面端共用构建；**不依赖任何 Tauri 能力**。
- 录音：1 秒切片即时落盘、暂停/继续/放弃、真实时长（暂停不计入）。
- 素材管理：编辑元数据、导入音频、纯文字记录、导出素材包、播放。
- **导出语义诚实**：只报"已发起导出"，绝不出现"电脑已接收"；取消/失败不算成功。
- 中断恢复：分片合并、连续性与可解码性校验、失败保留原分片、时长标注为估算值。
- 诊断记录：只记元数据（计数/字节/错误类别），**不含口述正文**。

### 阶段 D — PWA 与恢复 ⚠️（实现完成，待真机）
- 可添加到主屏幕、离线可用（Service Worker 带版本缓存与更新提示，**更新不打断录音**）。
- 中断检测与恢复入口、错误提示说明真实原因（非 HTTPS / 权限被拒 / 设备占用）。

### 阶段 E — 发布准备 ⚠️（部分完成）
- E1：Release 构建通过；**诊断日志已可用**（写入 `%LOCALAPPDATA%\com.voice-to-essay.app\logs\shengwen.log`）。**独立目录验证未做。**
- E2：生产构建通过；[手机端使用与恢复指南](手机端使用指南.md) 已完成（含**换网址前的资料迁出说明**）。**生产域名待定。**
- E3：见下节。

### 阶段外追加需求 ✅
- 自定义**热词表**（提升专有名词转写准确率），并让生成提示词内嵌"去 AI 味"约束。

## 三、还没做的

### 必须真机 / 人工完成（自动测试替代不了）
1. **iPhone 七类中断场景**：来电、锁屏、强退、刷新、关标签页、存储不足、长录音。
2. **Windows 独立目录完整流程**：录音 → 导入真实 M4A → 转写 → AI → 章节 → 导出 Markdown。
3. **编辑保护**：改正文后切换页面，取消离开应保留草稿。
4. **手机端导入音频端到端**：系统语音备忘录 → 播放 → 导出 → 电脑导入，音频完整。
5. **扩展格式探测**：webm / opus / amr / wma 能否被识别与转写。
6. **完整备份后在独立库恢复**（E3 第 10 步）。

### 功能缺口（已知且有意为之）
- **素材包只支持零依赖自实现容器**，桌面端 ZIP 容器未实现。
- **手机端导入音频不转码**（刻意设计，避免手机端引入解码依赖）。
- **导入素材的录制时间不自动填写**（文件名无法可靠反映时间）。
- **F 局域网传输**：计划安排在 E 验收之后，未开始。

### 技术债（不影响使用，但该知道）
- ⚠️ **Python 脚本有两份**：`python_stt/*.py` 与 `src-tauri/resources/python_stt/*.py`。
  后者由构建自动复制，但**已被提交进 git** → 改前一份时必须同步改后一份，否则发布版用旧逻辑。
  （`audio_probe.py` / `convert_audio.py` 目前只存在于前一份，靠构建时补齐。）
- ⚠️ **Rust 增量编译缓存会累积损坏**，报 `query stack during panic` 时跑 `tools/修复编译失败.bat`。
- 归档仍以内存读取为主（备份 ~1 GiB / 素材包 512 MiB / 手机预检 256 MiB 上限），海量资料需改流式。

## 五、建议的推进方式

- **一次只做一件事**，做完记录"预期结果 / 实际结果 / 证据"（这是计划里的交付模板要求）。
- **不要跳过 P0 直接做新功能**：E3 没走完，任何新功能都无法判断是否破坏主链路。
- 出问题就把**原始报错**发我，我来定位；我能代做的（编译、脚本、协议校验、代码修复）都不用你动手。
- **只有两件事必须你本人做**：真机操作、在 GUI 里点按钮。

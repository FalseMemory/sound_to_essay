# 《口述回归录》正文交付形态与存放位置

> 文档定位：澄清本仓库的"产物"到底是什么、产出后落在哪里、如何交付给读者。
> 关联审查项：P3-A（定位澄清 · 正文交付形态与存放位置）。

## 〇、一句话结论

**本仓库是「生产工具」，不是一份写好的《口述回归录》文稿。**
《口述回归录》的正文由本应用（录音 → 转写 → 整理 → 成章 → 导出）逐条产出，最终以「结构化草稿 + 导出文件」两种形态存在。

## 一、正文的两种存在形态

| 形态 | 存放位置 | 说明 |
| --- | --- | --- |
| **结构化草稿（活源）** | 资料库 SQLite（`data/oral_history.sqlite3`） | 章节草稿存于 `chapter_drafts` 表，每条记忆的多版文本存于 `text_versions` 表。这是可继续编辑、可回溯版本的"源头"，导出文件都是从这里生成的。 |
| **导出文件（交付物）** | 用户指定路径（本机任意位置） | 由应用内「单章导出 / 导出整本」生成。当前支持 **Markdown 合订（带来源注释）**；Word / PDF 为计划增强项。 |

> 关键区别：**SQLite 里的是"可编辑的活文档"，导出的 .md 是"某一时刻的快照"。** 修改应在 SQLite 草稿上进行，再重新导出。

## 二、正文在数据库里的落点（给开发者）

- **项目**：`projects` —— 一本回忆录通常对应一个 project。
- **记忆（最小素材单元）**：`memories` + `text_versions` —— 一段口述 = 一条 memory；其原始转写、校订稿、改写稿都是 `text_versions` 的不同版本（`version_type` 区分 `raw_transcription` / `ai_correct` / `ai_rewrite` / …，`tier` 区分 `faithful` 保真 / `creative` 创作）。
- **章节（成书结构）**：`chapters` + `chapter_memories`（关联）+ `chapter_drafts`（草稿）。
- **整本**：按 `chapters.sort_order` 顺序合订各章的"当前草稿"即得（见 `generate_book_markdown`）。

## 三、交付给读者的推荐流程

1. 在应用内完成录音转写、记忆整理（校订保真 / 文学化改写两档可选）。
2. 将记忆归入章节，用 AI 生成或手写为章节草稿。
3. 在章节列表点「导出整本」→ 选择保存路径 → 得到一份带来源注释的 Markdown。
4. （计划）后续支持 Word / PDF，并保留"来源记忆清单"与"时间未确认标注"，满足 DESIGN 的"可追溯 + 矛盾可见"硬约束。

## 四、关于《口述回归录》正文本身

本仓库**不含**任何成稿的回忆录文字（仓库内无 `.md/.txt` 形式的文稿；`sounds/` 仅 6 段示例录音）。
如果目标是交付一份完整的《口述回归录》，需要：

- **方式一（推荐）**：用本应用录入真实口述 → 转写 → 整理 → 成章 → 导出。正文自然落在上述数据库与导出文件中。
- **方式二**：人工撰写文稿后，作为"记忆 / 章节草稿"录入数据库（或直接写入导出模板），再走导出流程统一格式。

无论哪种方式，**正文的内容质量（错别字、语义、口述风格还原度）都取决于录音质量与整理档位的选择**，应用只负责提供"保真 / 创作"两档可控的整理能力，见 `风格回归基线样例.md`。

## 二、手机端实现

### `src/mobile/adapters/audioImport.ts`（新增）

**核心设计：不转码、不假定格式。**
手机端只负责把**原始字节**安全存下来，并如实记录格式信息；真正的解码/转码交给桌面端
（`audio_probe.py` + `convert_audio.py` + PyAV）。这样"支持多种格式"**不受浏览器解码能力限制**——
浏览器放不了的格式照样能导入并导出到电脑。

| 环节 | 做法 |
| --- | --- |
| 格式探测 | 魔数优先（RIFF/WAVE、OggS、fLaC、ID3、MPEG 帧同步、EBML、`#!AMR`、ASF、caff、FORM、`.snd`、`MAC `），ISO-BMFF 看偏移 4 的 `ftyp` 品牌（M4A/M4B/3gp/isom），最后回退扩展名表 |
| 认不出时 | 返回 `unknown` / `bin`，**不编造一个看起来合理的格式** |
| 时长 | 用 `<audio>` 的 `loadedmetadata` 读取（6 秒超时）；拿不到就**留空**，不猜默认值 |
| 可播放性 | 同一个探测顺带判定；**单列统计并在结果里如实说明** |
| 录制时间 | **不填**（沿用 B1 约定：录制时间不可靠时留空，不把导入时间冒充录制时间） |
| 存储 | 复用 `store.commitRecording(memory, blob)` —— 与录音同一条**原子提交**路径 |
| 大小上限 | 单文件 200 MB，超出即拒绝并说明原因（避免手机上内存被吃满） |
| 批量 | 逐个处理，**单个失败不影响其余**，结果逐条列出失败原因 |

配套改动：`MemoryStore.commitRecording` 的 `recordingId` 改为**可选**（导入没有分片与 pending 标记）。

### UI（`MaterialsView`）

## 三、桌面端扩展（不改变既有判定语义的部分）

1. **文件选择器**扩展名列表补全 webm / opus / amr / awb / wma / 3gp / m4b / caf / au / ape / wv / gsm 等。
2. **`python_stt/audio_probe.py` 的 `_sniff`** 补充魔数识别：
   EBML(webm/mkv)、`#!AMR`、ASF(wma)、caff、FORM(aiff)、`.snd`、`MAC `，以及 ISO-BMFF 的 M4B / 3gp 品牌。
3. **顺带修正一处既有判定**：原来 `RIFF` 开头一律判为 `wav`，但 RIFF 是通用容器
   （WebP 图片也是 RIFF）。现在要求 `RIFF` + `WAVE` 子类型才判 wav，否则回退扩展名。
   —— 这修掉了「把 WebP 当 WAV」的可能。

### 自检抓到并修掉的一个真实缺陷

`verify_audio_detect.ts` 首轮 24 项里 **2 项失败**：

```
FAIL 无扩展名且无魔数  → format=blob  (期望 unknown)
FAIL 空文件头          → format=empty (期望 unknown)
```

根因：`fileName.split('.').pop()` 在**没有点**时返回**整个文件名**，
于是 `"blob"` 被当成了扩展名。已改为显式实现 `extensionOf()`（用 `lastIndexOf('.')` 并处理
无点 / 隐藏文件 / 以点结尾三种情形）。修复后 24 项全通过。

> 这正是"只跑编译通过"发现不了的问题——格式判断错会把错误一路带到导出与桌面端导入。

## 七、已知限制

1. **手机端不做转码**：本机放不了的格式只能导出到电脑处理，这是刻意设计（避免在手机上引入解码依赖）。
2. **导入不自动填录制时间**：文件名无法可靠反映录制时间，交由用户补填。
3. **能解码 ≠ 内容完整**：截断的文件有时也能读出头部元数据，时长可能是错的。
4. 200 MB 上限是经验值，未在低端机上实测内存表现。

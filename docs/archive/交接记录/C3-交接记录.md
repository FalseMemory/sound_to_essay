## 任务编号

**C3．素材管理与导出**

## 完成内容

### 1. 素材列表：标题、时间、时长与保存／导出状态

每条素材显示：

- 标题、录音/记录时间
- 音频时长、格式（如 `M4A` / `WEBM`）、体积
- 状态徽标：**「本机保存」** 与 **「已导出 时间」/「未导出」**
- 人物标签（有则展示）

页头汇总「共 N 条 · 已导出 M 条」。

### 2. 播放

点播放按钮从 IndexedDB 取音频 → `URL.createObjectURL` → 播放；再次点击或播放结束即复位。
取不到音频时如实提示「找不到这条记录的音频数据（可能已被浏览器清理存储空间）」。

### 3. 编辑元数据

「编辑」进入与 C2 共用的 `MemoryEditor`：

- 可改：标题、正文、录音时间、模糊回忆时间（原文 + 精度）、人物、地点、标签、备注
- **保留 `recordId`，只递增 `revision`**——改内容不换 ID，否则跨设备去重与更新会失配
- 音频与导出状态原样保留，不会被编辑动作抹掉

### 4. 单条与多条导出

- **「导出全部 N 条素材」**：一次性打包全部
- **「导出」**（每条）：只打包这一条

### 5. 使用阶段 B 定义的素材包协议

新增 `src/mobile/adapters/packExport.ts`，在浏览器端生成 `.svpack`，容器格式与
`tools/make_pack_samples.py`（B2 参考实现）**逐字节对齐**：

```
[8]   magic "SVPACK1\0"
[u32] manifest 字节数（小端）
[32]  manifest 的 SHA-256（原始字节）
[..]  manifest JSON（UTF-8）
重复：
  [u32] 文件名长度
  [..]  文件名（UTF-8）
  [u64] 数据长度（小端）
  [32]  数据的 SHA-256（原始字节）
  [..]  数据
```

字段（camelCase）与协议一致：`formatVersion` / `packId` / `appVersion` / `exportedAt` /
`recordCount` / `audioCount` / `records{path,size,sha256}` / `audio[{assetId,path,format,size,sha256}]`，
`records.json` 中每条含 `recordId`、`revision`、`title`、`body`、`recordedAt`、
`eventDateText`、`eventDatePrecision`、`people`、`location`、`tags`、`notes`、`audio[]`。

**校验值以实际写入的字节重算**，保证包里声明的一定与内容一致。

### 6. 系统分享优先，文件下载兜底

`src/mobile/adapters/exporter.ts`：

1. 优先 Web Share Level 2（`navigator.canShare({files})`）→ 可直接「存储到文件」或发给其它 App
2. 不可用或异常时回退 `<a download>` 下载

### 7. 导出取消或失败不标记成功

只有 `shared` / `downloaded` 才写入 `lastExportedAt`；`cancelled` 与 `failed` **一律不标记**。

### 8. 「已导出」不等于「电脑已接收」

`ExportResult` **刻意没有**「电脑已接收」状态。文案如实：

- `shared` → 「已通过系统分享发出。请在目标应用里确认是否保存成功。」
- `downloaded` → 「已发起下载。浏览器不会告知是否真的保存成功，请到「文件」App 里确认。」
- `cancelled` → 「已取消导出，手机上的素材没有变化。」
- `failed` → 原始错误

### 9. 默认不在导出后删除手机资料

导出成功只更新 `lastExportedAt`，**不动音频与记录**，并明确提示「可以放心多次导出」。

### 10. 删除需要确认，并说明不可恢复

删除前二次确认，文案明确：会同时删除本机音频、**无法恢复**、建议先导出。

### 11. 缺失音频不伪装成完整导出

打包时若某条记录的音频在本机读不到，**跳过该音频并计数**，导出提示里明确
「有 N 条记录的音频在本机读不到，未包含在包内」。

## 跨实现互操作验证（重点）

手机端在浏览器打包、桌面端在 Rust 解析，是**两套独立实现**。只做类型检查与构建，
证明不了「手机上导出的包电脑能导入」。因此建了两层验证：

1. **`tools/verify_mobile_pack.ts`**（`npx tsx` 运行）
   调用真实的 `buildPack()` 生成 `tools/pack_samples/mobile_generated.svpack`（3 条记录、2 个音频、1 条纯文字），
   并自检容器头（magic / formatVersion / 记录数 / 音频数 / 条目路径）。

2. **桌面端 Rust 测试** `pack_import::tests::mobile_generated_pack_can_be_parsed_and_validated`
   用桌面端真正的解析路径 `parse_pack()` + `validate_pack()` 解析该文件，断言：
   - 3 条记录、0 缺失音频
   - 纯文字记录（`mobile-rec-3`）不带音频
   - 带音频记录的 `assetId` 能通过 manifest 反查回包里真实存在的文件条目

**结果：`cargo test --lib` → 10 passed / 0 failed**，互操作确认。

1. **仅支持 `.svpack` 容器**：桌面端 ZIP 容器尚未实现（受限于本机构建环境），

2. 导出文件名含中文（如 `声文素材包-20260919-1330.svpack`），
   个别 App 分享时可能对中文文件名处理不一致。
3. 时长在「中断恢复」的素材上是估算值（见 C2 交接记录）。

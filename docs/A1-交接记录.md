## 任务编号

**A1．录音与转写解耦**

## 完成内容

### 1. 录音分段落盘（不再整段驻留内存）

`Recorder` 原先把所有采样累积在 `Arc<Mutex<Vec<f32>>>`，只在 `stop()` 时才写 WAV——录音过程中崩溃即全部丢失。现改为：

- 录音开始前先创建**分片文件** `<uuid>.recording.pcm`（16-bit 单声道原始 PCM）与边车元数据 `<uuid>.recording.json`（采样率、声道、开始时间、格式、版本）。
- 音频回调线程降混为单声道后，通过**有界通道非阻塞投递**给专用写入线程（命名为 `rec-writer`）；磁盘 I/O 不发生在实时音频线程上，队列满时丢弃分块并告警，不会卡住采集。
- 写入线程**每个分块都 flush**，因此异常退出时已落盘部分可完整恢复。
- 帧数不入边车文件，而是由文件长度推导，避免录制过程中元数据过期。
- `stop()` 才把 PCM 流式转成 16-bit 单声道 WAV，**WAV 成功写出后**才删除分片文件。
- 分片写入的最后一个不完整样本（崩溃落在半字节）会被忽略，不会生成损坏 WAV。

### 2. 先登记，再转写

- 新增数据库表 `transcription_tasks`，记录转写任务的持久化状态。
- 新增命令 `register_recording`：在**一个事务内**创建记忆 + 音频资产 + `pending` 转写任务。
- 新增命令 `transcribe_memory`：把任务推进为 `processing`，调用 STT，成功写入 `raw_transcription` 文本版本并置 `success`；失败置 `failed` 并写入错误原因。
- 桌面资料库录音流程改为：`stop_recording` → `register_recording` → `transcribe_memory`，即**录音一落盘就被引用**，转写失败或应用崩溃都不会留下无人引用的孤儿音频。
- 创作区录音流程同步加固：先以空文本登记片段（音频被 `.vse` 项目引用），转写成功后再写入原始转写文本。

### 3. 转写任务状态可见、可重试

- 状态取值：`pending` / `processing` / `success` / `failed`。
- 新增命令 `list_transcription_tasks`。
- 资料库记忆列表显示「待转写 / 转写中 / 转写失败」徽标；记忆详情显示上次失败原因，并在任务非 `success` 时提供「开始转写 / 重新转写」按钮。

### 4. 重启恢复

- 新增 `reset_interrupted_transcriptions`：启动时把遗留的 `processing` 任务复位为 `pending` 并写明中断原因，杜绝"永久停留在处理中"。
- 新增 `recover_partial_recordings`：启动时扫描残留分片，只要有完整样本就转成可播放 WAV，并登记为记忆（标题带「⚠️ 恢复的录音」）+ 待转写任务，使抢救出的音频可被找到、播放与重新转写。
- 新增命令 `recover_interrupted_recordings`，并在应用启动流程中自动执行一次。

### 5. 清理动作的保护

- `cleanup_unreferenced_audio` 新增保护：转写任务持有的全部音频路径（含 `pending` / `processing` / `failed`）。
- 录制中的分片是 `.pcm` / `.recording.json`，而清理只扫描 `.wav`，因此录制中与待恢复资料天然不会被删除；清理时另外显式记录跳过的分片文件，便于诊断。

## 已知问题

1. **创作区（`.vse`）路径没有重新转写入口**。本次只做了数据安全加固（先登记再转写，失败不删）。资料库路径（阶段 A 的目标路径）具备完整状态与重试。
2. **恢复录音的归属项目是推断的**：优先用调用方传入的项目，其次最近更新的资料库项目，都没有则创建「录音恢复」。若你希望固定归属（例如总放进「待整理」项目），需要明确规则。
3. **录音进行中未禁止「清理录音」**。分片文件不会被删（扩展名不同），但同一时刻执行清理没有语义保护，建议后续加互斥。
4. 旧命令 `transcribe_audio` 仍保留给创作区使用，它本身仍是"先转写"的形态；创作区侧改用 `addClip` 先登记来兜底，但该命令没有任务状态。
5. 转写为单任务同步执行，无队列与并发上限；仅通过「任务非 `pending`/`failed` 不允许启动」防止同一任务重复并发。
